TERZO ADDENDUM COMPLEMENTARE
CONTROLLO SISTEMATICO DI TASTI, CREDENZIALI E AUTORIZZAZIONI
APPLICAZIONE “INDIA INSIEME”
VERSIONE DI RIFERIMENTO: 1.21.5

SCOPO DELL’ADDENDUM

Questo addendum non sostituisce e non ripete le checklist precedenti.

Serve a verificare in modo sistematico:

* che ogni funzione dichiarata esista realmente;
* che ogni tasto sia collegato a un’operazione reale;
* che l’interfaccia mostri soltanto le funzioni consentite;
* che il server applichi gli stessi permessi dell’interfaccia;
* che password, sessione personale e ruolo non entrino in conflitto;
* che un cambio di identità o di ruolo venga applicato immediatamente;
* che nessun utente possa utilizzare funzioni non comprese nelle proprie autorizzazioni;
* che ogni funzione sia verificabile mediante prove automatiche e manuali.

==================================================

==================================================

Prima del collaudo il programmatore deve produrre un inventario completo di tutti gli elementi interattivi presenti nell’applicazione.

Per ogni elemento registrare:

TESTO VISIBILE:

ICONA:

RUOLI AUTORIZZATI:

CREDENZIALE RICHIESTA:

RISULTATO ATTESO:

MESSAGGIO DI SUCCESSO:

MESSAGGIO DI ERRORE:

STATO OFFLINE:

TEST AUTOMATICO ASSOCIATO:

Il registro deve comprendere:

[ ] pulsanti con testo;

[ ] pulsanti contenenti soltanto icone;

[ ] collegamenti;

[ ] menu;

[ ] voci della barra inferiore;

[ ] voci della barra superiore;

[ ] schede;

[ ] selettori;

[ ] campi cliccabili;

[ ] fotografie cliccabili;

[ ] marker delle mappe;

[ ] notifiche cliccabili;

[ ] comandi presenti nelle finestre modali;

[ ] comandi visibili soltanto a determinati ruoli;

[ ] comandi generati dinamicamente.

Verificare che:

[ ] nessun tasto rimanga fuori dal registro;

[ ] nessun tasto sia privo di funzione;

[ ] nessuna funzione esista soltanto nel codice senza essere raggiungibile;

[ ] nessuna funzione dichiarata nella documentazione sia assente dall’interfaccia;

[ ] nessun endpoint operativo sia privo di controllo delle autorizzazioni.

==================================================
A2. MATRICE AUTORIZZATIVA UNICA
===============================

Il programmatore deve creare una matrice autorizzativa unica, utilizzata sia per lo sviluppo sia per i test.

COLONNE OBBLIGATORIE:

* Pubblico senza password;
* Familiare con password;
* Ospite autenticato;
* Viaggiatore proprietario;
* Viaggiatore non proprietario;
* Coordinatore;
* Sessione scaduta;
* Sessione revocata.

RIGHE OBBLIGATORIE:

* visualizzare contenuto;
* creare contenuto;
* modificare contenuto;
* eliminare contenuto;
* condividere contenuto;
* commentare;
* reagire;
* gestire profilo;
* gestire inviti;
* gestire documenti;
* gestire posizione;
* attivare notifiche;
* moderare;
* visualizzare log;
* revocare dispositivi.

Per ogni incrocio inserire:

[ ] CONSENTITO;

[ ] NEGATO;

[ ] CONSENTITO SOLTANTO SE PROPRIETARIO;

[ ] CONSENTITO SOLTANTO CON APPROVAZIONE;

[ ] NON APPLICABILE.

La matrice deve essere approvata prima di modificare il codice.

Non devono esistere regole differenti tra:

* frontend;
* API;
* database;
* documentazione;
* comportamento reale.

==================================================
A3. CONTROLLO DI COERENZA TRA INTERFACCIA E SERVER
==================================================

Per ogni operazione autorizzata:

[ ] il tasto deve essere visibile;

[ ] il tasto deve essere attivo;

[ ] il clic deve inviare la richiesta corretta;

[ ] il server deve autorizzare la richiesta;

[ ] il database deve registrare il risultato;

[ ] l’interfaccia deve mostrare il risultato.

Per ogni operazione non autorizzata:

[ ] il tasto deve essere nascosto oppure chiaramente disabilitato;

[ ] il server deve rifiutare comunque la richiesta diretta;

[ ] il database non deve essere modificato;

[ ] nessun file deve essere creato;

[ ] nessuna notifica deve essere inviata;

[ ] l’evento deve essere registrato nel log di sicurezza.

Eseguire il seguente controllo automatico:

[ ] confrontare tutti i tasti visibili per il Pubblico con gli endpoint accessibili al Pubblico;

[ ] confrontare tutti i tasti visibili al Familiare con gli endpoint accessibili al Familiare;

[ ] confrontare tutti i tasti visibili al Viaggiatore con gli endpoint accessibili al Viaggiatore;

[ ] confrontare tutti i tasti visibili al Coordinatore con gli endpoint accessibili al Coordinatore;

[ ] segnalare automaticamente ogni differenza.

ERRORE BLOCCANTE:

Un tasto visibile e apparentemente utilizzabile che viene sistematicamente rifiutato dal server deve essere considerato un difetto bloccante.

A4. MACCHINA DEGLI STATI DELLE CREDENZIALI
==========================================

Devono essere definiti e collaudati separatamente i seguenti stati:

STATO 1

* nessuna password;
* nessuna sessione;
* nessun profilo collegato.

STATO 2

* password di gruppo corretta;
* nessuna sessione personale;
* nessun profilo collegato.

STATO 3

* password di gruppo corretta;
* profilo memorizzato localmente;
* nessuna sessione valida.

STATO 4

* sessione Ospite valida.

STATO 5

* sessione Viaggiatore valida.

STATO 6

* sessione Coordinatore valida.

STATO 7

* sessione scaduta.

STATO 8

* sessione revocata.

STATO 9

* token presente localmente ma non riconosciuto dal server.

STATO 10

* password memorizzata ma successivamente modificata sul server.

Per ogni stato verificare:

[ ] etichetta di accesso mostrata;

[ ] identità mostrata;

[ ] ruolo mostrato;

[ ] tasti visibili;

[ ] tasti nascosti;

[ ] endpoint autorizzati;

[ ] comportamento al ricaricamento;

[ ] comportamento dopo riapertura;

[ ] comportamento dopo ritorno online;

[ ] messaggio mostrato all’utilizzatore.

==================================================
A5. PRECEDENZA TRA PASSWORD E SESSIONE
======================================

Verificare i casi in cui sul dispositivo siano presenti contemporaneamente:

[ ] password di gruppo e sessione Viaggiatore;

[ ] password di gruppo e sessione Coordinatore;

[ ] password di gruppo e sessione scaduta;

[ ] vecchio profile_id e nuova sessione;

[ ] vecchio nome locale e nuova sessione;

[ ] sessione A e dati locali del profilo B.

La regola obbligatoria deve essere:

[ ] l’identità server della sessione prevale sempre sui dati modificabili del browser;

[ ] il ruolo restituito dal server prevale sempre sul ruolo locale;

[ ] profile_id della sessione prevale sempre sul profile_id del localStorage;

[ ] il nome dell’autore viene determinato dal server;

[ ] la password comune non aumenta i privilegi di una sessione personale;

[ ] una sessione scaduta non viene recuperata utilizzando silenziosamente un vecchio profilo locale;

[ ] nessun utente può risultare contemporaneamente Viaggiatore A e Viaggiatore B.

[ ] fotografia;

[ ] bozze personali;

[ ] documenti;

[ ] posizione;

[ ] preferiti;

[ ] notifiche non lette;

[ ] autorizzazioni;

[ ] menu del ruolo;

[ ] link personali;

[ ] dati privati nella cache.

Ripetere:

[ ] da Viaggiatore a Coordinatore;

[ ] da Coordinatore a Viaggiatore;

[ ] da Viaggiatore a Pubblico;

[ ] da Coordinatore a Pubblico;

[ ] da Familiare a Viaggiatore.

==================================================
A7. CAMBIO DI RUOLO DURANTE UNA SESSIONE APERTA
===============================================

CASO A – PROMOZIONE

[ ] Accedere come Viaggiatore.

[ ] Lasciare l’app aperta.

[ ] Promuovere l’utente a Coordinatore da un altro dispositivo.

[ ] Verificare aggiornamento della sessione.

[ ] Verificare comparsa dei nuovi comandi soltanto dopo conferma server.

[ ] Verificare che non sia necessario cancellare manualmente la cache.

CASO B – RETROCESSIONE

[ ] Accedere come Coordinatore.

[ ] Lasciare aperta la dashboard.

[ ] Cambiare il ruolo in Viaggiatore.

[ ] Verificare scomparsa immediata dei comandi da Coordinatore.

[ ] Tentare di utilizzare un tasto rimasto aperto.

[ ] Risultato atteso: richiesta rifiutata.

[ ] Verificare impossibilità di utilizzare la cronologia del browser per tornare nella dashboard autorizzata.

CASO C – REVOCA COMPLETA

[ ] Revocare il dispositivo mentre è aperta una finestra privata.

[ ] Utilizzare un comando già visibile.

[ ] Verificare rifiuto immediato.

[ ] Chiudere automaticamente i dati privati già mostrati.

Verificare che il controllo venga eseguito:

[ ] prima della lettura;

[ ] prima della modifica;

[ ] prima dell’eliminazione;

[ ] prima del download;

==================================================
A10. RISPOSTA MINIMA DEL SERVER IN BASE AL RUOLO
================================================

Verificare che il server non restituisca dati che il frontend si limita successivamente a nascondere.

PUBBLICO

[ ] riceve soltanto campi pubblici;

[ ] non riceve ruoli amministrativi non necessari;

[ ] non riceve dati dei documenti;

[ ] non riceve posizioni private;

[ ] non riceve identificativi interni non necessari.

FAMILIARE

[ ] riceve soltanto contenuti autorizzati ai familiari;

[ ] non riceve dati del gruppo riservato;

[ ] non riceve documenti;

[ ] non riceve sessioni o inviti altrui.

VIAGGIATORE

[ ] riceve soltanto i propri documenti;

[ ] riceve soltanto le posizioni consentite;

[ ] non riceve dati amministrativi del Coordinatore;

[ ] non riceve log non autorizzati.

COORDINATORE

[ ] riceve esclusivamente le informazioni necessarie al coordinamento;

[ ] non riceve token o segreti;

[ ] non riceve dati cancellati.

=============================================

Ogni tasto deve essere verificato nei seguenti stati:

[ ] normale;

[ ] puntato;

[ ] premuto;

[ ] attivo;

[ ] disabilitato;

[ ] caricamento;

[ ] operazione riuscita;

[ ] operazione fallita;

[ ] rete assente;

[ ] sessione scaduta;

[ ] autorizzazione negata;

[ ] operazione già eseguita.

Per ogni tasto verificare:

[ ] il primo tocco viene rilevato;

[ ] un tocco prolungato non genera operazioni impreviste;

[ ] un doppio tocco non duplica l’operazione;

[ ] dieci tocchi rapidi non generano dieci richieste;

[ ] il tasto disabilitato non genera richieste;

[ ] il caricamento impedisce una seconda operazione incompatibile;

[ ] l’etichetta cambia in modo comprensibile;

[ ] il tasto torna utilizzabile dopo un errore;

[ ] il tasto non rimane permanentemente bloccato;

[ ] il risultato corrisponde all’azione indicata.

[ ] tasti coperti da altri elementi;

[ ] tasti fuori dallo schermo;

[ ] tasti visibili ma non raggiungibili da tastiera.

Ogni elemento rilevato deve essere:

[ ] completato;

[ ] rimosso;

[ ] disabilitato con indicazione “Non ancora disponibile”;

[ ] documentato come funzione non completata.

A16. TEST DEI TASTI DISTRUTTIVI
===============================

Per ogni funzione che elimina, revoca o sovrascrive:

[ ] usare un colore e un testo riconoscibili;

[ ] indicare esattamente cosa verrà eliminato;

[ ] richiedere conferma;

[ ] distinguere Annulla e Conferma;

[ ] impedire conferma accidentale tramite doppio tocco;

[ ] mostrare stato dell’operazione;

[ ] impedire chiusura ambigua durante l’esecuzione;

[ ] comunicare completamento;

[ ] aggiornare immediatamente tutte le schermate coinvolte;

[ ] verificare se esiste possibilità di recupero;

[ ] registrare l’operazione nel log.

Controllare in particolare:

[ ] nessun tasto Elimina occupi la posizione normalmente usata da Annulla;

[ ] nessuna pressione del tasto Indietro confermi l’eliminazione;

[ ] nessuna operazione venga eseguita due volte.

==================================================
A17. TEST DELLE NEGAZIONI E DEL RECUPERO
========================================

Quando un’operazione viene negata per mancanza di autorizzazione:

[ ] spiegare quale autorizzazione manca;

[ ] non utilizzare soltanto “Errore”;

[ ] non mostrare dettagli tecnici;

[ ] non cancellare ciò che l’utente ha scritto;

[ ] non perdere allegati selezionati;

[ ] offrire accesso o collegamento del profilo, se appropriato;

[ ] consentire di tornare alla schermata precedente;

[ ] non entrare in un ciclo continuo di richieste;

[ ] non ripetere automaticamente una richiesta vietata;

[ ] non utilizzare la password comune per aggirare il rifiuto.

Esempi di messaggi richiesti:

* “Questa funzione è disponibile soltanto al Coordinatore.”
* “Puoi modificare soltanto il tuo profilo.”
* “Puoi aprire soltanto i documenti associati al tuo profilo.”
* “La sessione è scaduta. La bozza è stata conservata.”
* “Questo dispositivo è stato revocato.”
* “Per continuare devi utilizzare il tuo invito personale.”
